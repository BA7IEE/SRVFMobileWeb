## 0. 给开发执行者的总指令

按照本文件直接完成前端基础工程和可交互页面，不再重新讨论已经确定的产品范围。可以在组件拆分、局部排版和文件命名上作合理选择，但不得自行扩大业务。

**必须做：**

1. 建好工程、布局、路由、类型、模拟数据访问层、环境隔离和质量检查。
2. 完成 13 个主页面及必要子流程，页面之间能真实跳转，模拟操作前后状态一致。
3. 完成登录态恢复、过期、模拟续期、退出、账号切换、路由准入和活动级权限展示。
4. 完成动态表单、保险表单、文件本地选择、防重复提交、草稿和各种失败状态。
5. 完成扫码、相机和定位的适配边界与模拟场景；不把模拟签到当成真实签到。
6. 提供自动化测试、人工验收脚本、截图和实际执行报告。
7. 按 §15.4 复用 SRVF 品牌 tokens，并完成真实组件计算样式检查。
8. 按 §9.6 完成已知端点的离线协议适配与测试；纯客户端假设与真实契约严格分开。

**不得做：**

- 不连接 `dp.srvf.team`、生产域名或任何其他真实业务服务，不使用真实测试账号。
- 不发送真实登录、短信、微信授权、保险审核、报名、打卡、上传或结算请求。
- 不改后端仓库、数据库、迁移、权限配置和任何业务开关。
- 不为了跑通演示，把缺失接口伪装成已有接口，或把模拟数据混入真实数据。
- 不把旧考勤的页面、SDK、写接口重新搬进新项目。
- 不把“前端校验通过”写成“身份已核实”“保险有效”“签到已正式入账”。
- 不擅自创建远程仓库、推送到主分支、合并 PR 或公开发布演示站。

**完成标准：**本地启动后，可以切换模拟场景，演练“登录 → 查看活动 → 处理保险 → 报名 → 查看结果 → 模拟考勤 → 查看模拟认定记录”；网络检查证明没有真实业务请求。

## 1. 本阶段到底做到什么程度

### 1.1 三类工作必须分开

| 类别         | 本阶段要求                                                               | 不代表什么                                   |
| ------------ | ------------------------------------------------------------------------ | -------------------------------------------- |
| 真实前端能力 | 布局、路由、状态管理、表单验证、文件本地预览、错误恢复、测试真实可运行   | 不代表后端业务已可用                         |
| 模拟业务交互 | 使用固定测试数据演练报名、保险审核结果、考勤状态和角色差异               | 不代表已验证真实身份或产生真实业务事实       |
| 接线准备     | Port、页面模型、固定契约证据、请求构造、响应映射、离线契约测试和缺口交接 | 不代表已连接服务、缺口已实现或真实权限已验收 |

不要只做“点击按钮弹出成功提示”的假交互。也不要为了模拟，把后端资格、容量分配、保险审核和贡献结算完整复制到浏览器中。

### 1.2 冻结的产品范围

- 普通队员端 9 个主页面：登录、活动列表、活动详情、活动报名、我的活动、扫码考勤、我的参与记录、我的保险、我的。
- 负责人端 4 个主页面：我负责的活动、报名管理、现场考勤工作台、人员核验与异常。
- 底部导航固定为：**活动｜我的活动｜我的**。
- 首发不做招新、证书申报、入队申请、手机端活动创建、复杂活动审批、离线考勤、批量导入和完整版结算管理。
- 复杂认定、审核和结算计划由管理端承接；管理端是否已经接通新版，属于后续联调前置核验，不能由本前端默认认定。

### 1.3 本阶段与后端清理的关系

旧考勤退役已有单独任务 #1408。前端按新版目标建设，不等待旧代码全部清理完才开始搭建，也不因本阶段页面完成就宣称切换已经完成。

本阶段先完成全部界面、模拟演练和已知契约的离线适配；后端测试期间可同步交接缺口和契约变更，不执行真实业务调用。后续获准连接时，再核对部署 SHA、契约差异、权限和新流程状态。旧代码是否已全部删除不是 mock 施工的前置条件，但新版实际可用是上线前置条件。

## 2. 工程选型：够用即可

### 2.1 必选项

| 项目           | 选择与用途                                         |
| -------------- | -------------------------------------------------- |
| 页面框架       | Vue 3，Composition API，`<script setup lang="ts">` |
| 语言           | TypeScript，开启 strict                            |
| 构建           | Vite                                               |
| 组件           | Vant 4，统一主题和公共样式                         |
| 路由           | Vue Router，命名路由、路由元信息、导航守卫         |
| 全局状态       | Pinia，仅保存确实跨页面共享的状态                  |
| 样式           | CSS 变量 + 页面局部样式；不再引入另一套大型 UI 库  |
| 表单验证       | Vant Form 配合可独立测试的 TypeScript 验证函数     |
| 单元／组件测试 | Vitest + Vue Test Utils                            |
| 浏览器测试     | Playwright                                         |
| 代码质量       | ESLint、格式化检查、`vue-tsc`                      |
| 包管理         | pnpm，提交锁文件                                   |

实施时选择相互兼容的稳定版本，固定实际解析版本并记录 Node、pnpm 和依赖版本。不要在文档中臆造“最新补丁版”，不要为了追新跨大版本迁移。

### 2.2 本阶段不引入

不引入 SSR、微前端、低代码平台、自建组件库平台、独立权限引擎、PWA／Service Worker、复杂离线同步和新的后端服务。

暂不引入额外请求缓存框架或两套表单验证库。先用清晰的数据访问接口、少量 composable 和 Pinia 完成需求。模拟数据优先直接通过本地异步适配器提供，不必为它单独搭一个 HTTP 服务器。

### 2.3 路由模式

本阶段采用 Hash 路由，便于静态预览时直接刷新子页面。内部仍使用标准路径和命名路由，业务组件不拼接 `#`。路由实例统一读取部署 base，后续需要改 History 模式时只修改路由入口及部署配置。[T1]

这是本阶段的交付选择，不是要求业务 API 改成 Hash，也不意味着前端路由等于后端路由。

## 4. 环境隔离与“零真实 API”约束

### 4.1 数据源只有一个选择点

| 模式           | 行为                                                                                                              |
| -------------- | ----------------------------------------------------------------------------------------------------------------- |
| `mock`         | 只加载本地模拟适配器；全局可见“演示模式 · 数据不是真实记录”                                                       |
| `unconfigured` | 展示“服务尚未接通”；不加载模拟身份，不允许任何业务提交                                                            |
| `api`          | 本阶段禁止启用真实网络；配成此值立即报错。允许提前实现注入式请求／响应适配器，仅在离线契约测试中使用；不回退 mock |

建议约定 `VITE_DATA_SOURCE`。其余环境变量按确实需要再加，不预埋真实域名、账号或密钥。

`.env.mock` 只包含公开、非敏感演示配置；默认普通构建使用 `unconfigured`。Vite 的 `VITE_*` 会进入客户端产物，不能用于存放秘密。[T2]

### 4.2 必须提供的命令

| 命令                    | 预期行为                                                                        |
| ----------------------- | ------------------------------------------------------------------------------- |
| `pnpm dev`              | 显式以 mock 模式启动本地开发                                                    |
| `pnpm build:mock`       | 生成带演示标识的模拟预览包，例如输出到 `dist-mock`                              |
| `pnpm preview:mock`     | 预览上述模拟产物，默认仅监听本机                                                |
| `pnpm build`            | 生成不含模拟业务入口的 unconfigured 产物；业务停在未接线提示                    |
| `pnpm typecheck`        | Vue 与 TS 类型检查                                                              |
| `pnpm lint`             | 静态检查                                                                        |
| `pnpm format:check`     | 格式检查                                                                        |
| `pnpm test:unit`        | 非交互运行单元／组件测试                                                        |
| `pnpm test:e2e`         | 启动本地 mock 服务并执行浏览器测试                                              |
| `pnpm test:contract`    | 已核实契约的序列化、解析、错误和恢复测试，使用注入式假传输，零网络              |
| `pnpm check:contract`   | 校验本地契约来源／摘要／覆盖表，识别缺口和未经确认的版本变化，不自动拉远程 main |

构建脚本必须防止通过外部环境变量把普通构建悄悄变成 mock。显式 `build:mock` 可以生成优化后的模拟包，但仍不是生产业务版本；不能只用 `import.meta.env.DEV` 判断是否允许 mock。

### 4.3 网络边界

本阶段运行时只允许加载本站静态资源和开发工具必要连接。不请求真实 API、第三方统计、在线字体、图床、远程地图或微信 SDK 配置。

浏览器测试必须记录请求：

- 所有 `/api/` 业务请求均应为 0。
- 对 `dp.srvf.team` 和其他真实业务域名的请求均应为 0。
- HTTP、XHR、fetch 之外，也要检查 WebSocket、EventSource、Beacon、表单提交和资源 URL 没有绕过。
- 开发服务器 HMR 连接属于工具链，不属于业务 API；测试应明确区分。
- 不使用 Service Worker，避免缓存或拦截掩盖真实请求。

Playwright 可监控和拦截浏览器网络请求，验收需保留实际请求证据，而不是只写“已使用 mock”。[T3]

### 4.4 构建产物、网络与开关的三重检查

不能只扫描源码中的 `fetch` 字符串。实施时至少同时做：

1. 静态导入检查：业务页面不得直接读 fixture 或网络；后台 `src/utils/http`、`src/utils/auth`、Admin SDK 不得进入移动端依赖图。
2. 产物检查：普通 `dist` 中没有合成队员名单、演示密码、场景控制代码、`SRVF-DEMO:` 数据；构建入口不能被 query、localStorage 或环境变量优先级偷偷改成 mock。[T2]
3. 运行时检查：使用全新浏览器 context，关闭 Service Worker，允许本地静态资源、必要 HMR，其余网络直接拒绝并记录失败。[T3]

离线契约测试使用 `FakeTransport` 直接返回内存响应，不经浏览器 fetch、不起假业务服务器；因此不豁免“业务请求为 0”的验收。`wire` 目录可含已核实的相对 API 路径用于测试，但不能包含真实凭证或自动实例化网络客户端。

为本地预览准备 CSP 模板：构建后的 mock/unconfigured 版原则上 `connect-src 'none'`，开发 HMR 单独放行本地连接；静态图片按需要放行 `self/blob/data`，二维码只允许受控 Blob 图片。是否实际配置成功以响应头和浏览器检查为准，不把一份模板当成已部署安全措施。

本阶段不公开部署预览；真机局域网 HTTPS 预览另按授权环境进行。相机调用可能由浏览器或操作系统处理本机权限，不能宣称能证明操作系统层面完全没有任何网络访问。

## 6. 页面逐项落地要求

### U01 登录

- 账号、密码、显示密码开关、提交中状态、错误信息和登录帮助。
- 登录页清楚提示“仅演示账号，请勿输入真实密码”。演示身份可快捷选取，也必须能测试表单路径。
- 不以任意非空输入自动登录成功；mock 适配器有明确的演示账号校验及失败场景。
- 不假定队员编号、手机号、邮箱均可作为登录名；展示“账号”，具体正式登录名格式待接线确认。
- 已登录再次进入 `/login`，返回安全目标或活动列表，避免循环跳转。

### U02 活动列表

- 提供列表、关键词、活动类型及“可报名”等视图状态；模拟数据至少包含可报、已截止、已结束、受邀、本人不可见情境。
- 搜索防抖、请求取消和过时结果丢弃；不要让旧搜索结果覆盖新搜索。
- 筛选变化重置分页；加载更多去重；不能对当前一页做过滤却显示成“全库筛选”。
- 列表滚动及筛选可记忆，退出或换账号时清理本人相关缓存。
- 不对每张卡片额外串行查询多个详情，不以页面加载完毕作为报名资格已确认。

### U03 活动详情

按重要性排列：标题与活动状态、时间地点、本人报名／场次结果、场次岗位、要求与说明、保险条件、底部主操作。

- 同一页面处理未报名、已提交、部分场次通过、候补、取消、结束等不同状态。
- 已结束或取消的活动仍应展示安全的历史摘要，不调用普通详情失败后整页白屏。
- 活动“已到结束时间”和“已正式完成结算”是两件事，不互相替代。
- 资格加载中或未知时显示“正在核对／暂无法确认”，不先亮起可提交按钮。
- 保留分享链接入口的结构，只分享本站活动路径；本阶段不接微信分享 SDK。

### U04 活动报名

- 按真实界面需求完成场次选择、岗位志愿排序、八种动态题型和最终确认页。
- 无复杂表单的活动应更简洁，不强行拆成多个空步骤。
- 保险缺失时可跳至 U08，并在同一会话内返回原报名位置；返回后重新读取资格。
- 成功返回先显示“报名已提交（演示）”，再展示模拟的分配结果；不能直接假定审核通过。
- 修改报名只在模拟动作结论明确允许时开放；不得因表单可编辑就允许改已确认的岗位。
- 取消报名是独立确认动作，保留历史结果，不通过本地删掉一张卡片假装后端已取消。

### U05 我的活动

- 按“近期／全部”等清楚维度展示，报名状态和活动阶段分别标注。
- 显示每个场次的实际模拟结果：例如上午通过、下午候补；头部状态不能覆盖场次差异。
- 签到入口只出现在正确场次，不让用户误对整场多日活动只签一次。
- 没有报名关联的临时参与能否进入此列表，属于真实接口覆盖问题；不能把报名列表当完整出勤历史。[B2M]

### U06 扫码考勤

- 展示活动、场次、岗位（可得时）、当前在场状态、下一步提示与扫码按钮。
- 完整处理扫码准备、识别、确认、提交中、成功、失败和结果未知。
- 不因“当前没有开放服务段”就显示“从未签到”；可能已签退过，需区分“当前不在场”和历史事实。
- 服务端下一动作提示不等于最终授权，还可能被二维码、时间窗、资格或位置条件拒绝。
- 本阶段签到成功文案必须带演示属性；没有生成正式时长或贡献。

### U07 我的参与记录

- 使用独立的参与记录模型，不把“我的报名”换个标题当考勤记录。
- 当前记录、处理中状态、正式认定结果分开显示；没有结果不等于零小时。
- 本阶段准备“无记录、待认定、已认定、更正后结果、历史活动信息受限”场景。
- 展示数据层给出的正式汇总，不在页面把打卡时间差、分页记录或新旧数据相加。
- 原始账本分录若有冲回／重记，不应以正数求和误报总贡献；正式净额仍待后端权威读面。

### U08 我的保险

- 分为“队伍统一保险”和“本人登记的自购保险”。没有自购记录不等于没有统保。
- 自购保险有新增、修改、删除确认、审核状态、保障日期与版本冲突处理。
- 实质修改已审核记录后，演示数据应进入待审核；普通队员没有“审核通过”按钮。[B7W]
- 从报名进入时显示“针对本次活动的保险条件”；普通“我的保险”页面显示当前概览，两者不混淆。
- 本阶段不加保险商品、购买链接、支付和自动投保。
- 既有自购接口未提供保单附件写入；本轮不把“上传保单”做成可用业务，必要材料由后续单独确认。[B7C]

### U09 我的

- 显示模拟队员编号、姓名／昵称、身份；无值显示“未提供”，不编造组织归属。
- 入口保留：我的保险、参与记录、账户设置、我负责的活动（有条件）、帮助、退出。
- 不显示证书、招新等未开发入口形成大量“敬请期待”。
- “我负责的活动”是工作入口，不要求用户切换成管理员账号。

### F01 我负责的活动

- 同一人可能只负责报名、只负责考勤或两者都有。
- 列表与详情都按活动范围判定，不能把一个活动的职责扩散到全部活动。
- 职责已撤销、活动不存在、服务错误应有不同场景；不可读记录不保留敏感缓存。

### F02 报名管理

- 展示报名人安全标签、整体及场次状态、必要摘要，不展示保单号、原始定位等无关信息。
- 先到先得、排序／抽签与人工审核不是同一操作链；只根据数据层给出的可执行动作显示按钮。
- 不把所有 `pending` 都翻译成“负责人点通过即可”，不在本前端实现分配算法。[B3A]
- 批量操作显示成功数量和逐项失败；整体请求返回不等于全部成功。
- 切换筛选或活动后清除不适用选择，确认框说清楚本次对象和范围。

### F03 现场考勤工作台

- 明确当前活动和场次，分别管理签到码与签退码。
- 生成、展示、失效、撤销、重签都用模拟数据演练；有版本冲突时刷新，不覆盖。
- 模拟二维码使用专属演示格式；不使用真实签名、不展示真实 token。
- 工作台统计从模拟读面获取，不用当前分页人数冒充全场已签到人数。
- “现场操作结束”不等于“正式结算完成”，不得出现一键直接入账。

### F04 人员核验与异常

- 工作人员扫成员码与队员扫场次码共用底层扫码组件，但流程和输入类型严格区分。
- 代签前确认活动、场次、人员和动作，填写原因；不能只靠姓名匹配目标。
- 本轮做最小的受控代签／代退表单及明确结果；复杂历史更正编辑器不纳入范围。
- 提前离场、更正处理中等以模拟结果展示，不由前端计算认定金额、分值或时长。
- 所有异常列表来源不足的地方标为后续读接口缺口，不用旧 GPS 证据列表冒充新事件列表。

## 7. 登录态、会话与路由准入

### 7.1 不能只用一个 `isLoggedIn`

客户端至少区分以下状态；名称可调整，语义必须保留。

| 状态            | 含义                                 | 页面行为                           |
| --------------- | ------------------------------------ | ---------------------------------- |
| `initializing`  | 正在恢复会话及确认身份               | 显示启动占位，不闪现受保护内容     |
| `anonymous`     | 未登录                               | 去登录，记住安全的原目标           |
| `authenticated` | 会话可用且身份已加载                 | 继续判断成员准入和活动范围         |
| `refreshing`    | 正在模拟续期                         | 合并续期请求，暂停依赖新凭证的动作 |
| `expired`       | 确认会话不可恢复                     | 清理敏感状态，提示重新登录         |
| `blocked`       | 已识别账号但成员未绑定／停用／不可用 | 显示准入说明，不伪装成密码错误     |
| `unavailable`   | 无法确认会话，例如临时读取错误       | 显示重试，不当作已退出或已经授权   |

全局身份与活动范围权限是两个层次。登录成功不等于能使用成员功能，能使用成员功能不等于能管理该活动。

### 7.2 启动与导航顺序

```text
应用启动
  → 安装 Pinia
  → 创建／注入唯一数据访问实例
  → 只执行一次 restoreSession
  → 加载模拟身份和能力
  → 路由守卫判断
       未登录 → 登录页
       成员不可用 → 准入说明
       活动管理范围未知 → 加载或重试
       无权 → 403／安全的不可用页
       允许 → 目标页面
```

Vue Router 的 `meta` 与导航守卫可承载页面准入；Pinia 在组件外使用时应确保实例已经安装或显式传入。[T4][T5]

必须处理：刷新受保护页面、直接打开深链接、登录后回原页、浏览器后退、账号切换、刷新期间退出、多个组件同时请求身份。

### 7.3 模拟会话存储

- 演示会话只保存合成身份引用、模拟会话 ID、过期时间和场景编号，不保存用户输入的密码。
- 优先使用命名空间隔离的 `sessionStorage`，例如 `srvf:mock:v1:*`；必须有版本、过期和异常反序列化处理。
- 这些记录只为模拟页面刷新，**不是安全凭证**。用户可修改浏览器存储，本阶段不声称能防止这种篡改。
- 不提供“记住密码”，不把正式 access token／refresh token 的存储方案提前定死。
- 后续真实凭证怎么保存，需结合后端认证契约、部署域名及安全方案单独确认；不要直接沿用演示存储。

### 7.4 过期与续期演练

- 通过注入时钟模拟短会话和长会话到期，不等待真实时间。
- 同时发生 5 个需要续期的请求，只触发一次续期；其他请求等待同一个结果。
- 续期成功只重新执行允许重放的读取；写操作不能因为续期成功就自动重新提交。
- 续期确认失败，统一进入过期状态；临时网络错误进入不可用状态，不错误清除所有上下文。
- 模拟“退出后旧续期才返回”：旧响应不得重新把用户登录回来。
- 为每次身份会话维护递增的 `sessionEpoch` 或等价标记，拒绝上个账号的迟到响应。
- 权限不足不等于登录过期。未来错误映射中不能将所有 403 当作退出登录。

### 7.5 退出与账号切换

退出后同时清理：身份、权限投影、本人业务缓存、敏感草稿、待提交意图、扫码凭证、对象 URL、相机流和轮询任务。

主动退出可先提醒未保存内容；身份被撤销或账号不可用时，安全清理不得被一个确认弹窗无限阻塞。

重新登录其他账号后，上一账号的数据不能在列表、保险、二维码、草稿和浏览器后退页面中重新出现。

### 7.6 安全返回目标

优先保存“命名路由 + 白名单参数”，而不是直接信任 `redirect` URL。必须拒绝外部地址、协议相对地址、恶意编码、未知路由以及不符合当前权限的目标。

返回路径只允许本站业务路由；不携带密码、保单号、文件内容或扫码 token。无法使用原目标时返回活动列表。

### 7.7 登录表单验证

- 账号去除首尾空白；本轮补核的 `LoginDto` 为 3—32 位字母、数字、下划线或中横线，按固定契约提供验证，不假定手机号／队员编号直接等于登录名。规则集中在契约验证处，更新必须有版本证据。[N1]
- 密码检查非空，不 `trim()`、不自动改变大小写、不自动截断。
- 不把注册时的复杂度要求强加到登录密码上。
- 点击与回车共用提交函数；输入法组合输入期间不误触发提交。
- 错误密码、限流、服务不可用、成员不可用分别有模拟反馈。
- 修改密码子流程至少校验旧密码非空、新密码非空、二次输入一致；正式新密码规则须读取对应固定 DTO 并记录证据，未核实前只能标“界面规则待对齐”，不能把登录密码的规则套过去。

---

### 7.8 提前做认证契约演练，不等真实上线

本轮核实：密码登录响应为 `accessToken / tokenType / expiresIn / refreshToken / refreshExpiresAt` 五个字段；不包含完整队员资料和权限。刷新会返回新 access 与 refresh，refresh family 的绝对到期时间不因此延长。[N1]

现在就应通过合成响应实现并验证：

- 登录返回凭证 → 独立加载本人资料和产品能力 → 确认成员准入。第二步失败不是“已可使用全部业务”。
- `expiresIn` 按固定契约中的时长字符串解析，不当作 ISO 日期或 Unix 时间戳；解析失败转契约错误，不默默假定还能用 15 分钟。单位、上界和异常值有测试。
- `refreshExpiresAt` 单独维护；本地时钟只用于体验提示，服务端拒绝始终有效。刷新后原子替换整组凭证，不混用新 access 与旧 refresh。
- 同一会话并发刷新只有一个执行者；刷新成功、明确拒绝、临时失败、被取消均须使所有等待者结束，不产生永远 pending 的请求。
- **刷新请求已可能被处理但响应丢失**与“刷新明确未发送”分开。没有契约证明可安全重试时，不拿旧 refresh 自动循环重试；界面提示重新认证，不能把它当普通 GET 重试。
- 认证队列必须绑定 `sessionEpoch`。账号切换、主动退出、成员被停用后，旧刷新结果不可重新写入身份。
- 401 的登录失败、access 失效、refresh 失效分别映射；403 不自动刷新；没有已证实的错误类别不根据 HTTP 状态猜业务含义。
- 已发出的写操作不参与全局“刷新成功后全部重放”；依 §12.4 的逐操作策略决定。

**存储决策也要现在形成 ADR，不拖到最后。** `CredentialStore` 保持可替换；模拟凭证与真实凭证命名空间、生命周期完全隔离。不复制后台的 `authorized-token / user-info / multiple-tabs` 存储键及原始权限缓存。[A6]

ADR 至少比较：仅内存、限定会话存储以及已有服务是否能支持安全 Cookie。不得假装纯前端能创建 HttpOnly Cookie，也不为本阶段新增认证后端。记录选定方案、刷新／关页体验、XSS 风险、跨标签页协调和登出语义；未批准的真实存储策略是接线阻塞项，而不是阻塞 mock 开发。

多标签页必须在一种明确策略下测试：每页独立登录并获得独立 family，或同一共享 family 有唯一刷新协调者。**不能把 sessionStorage 复制标签页后仍称为“天然不会共享凭证”。** 不通过广播发送密码或完整 token；同步的重点是会话版本、退出和失效。所有真实认证验证仍为后续 NOT_RUN。

## 8. 权限展示与准入验证

### 8.1 三层判断

| 层级         | 用途                     | 本阶段实现                 |
| ------------ | ------------------------ | -------------------------- |
| 成员准入     | 是否能使用成员 H5        | 模拟未绑定、停用、正常成员 |
| 产品能力     | 是否展示某类入口         | 例如是否出现“我负责的活动” |
| 具体活动动作 | 能否对某活动执行特定操作 | 报名管理、考勤管理分别判断 |

现有产品能力只是入口提示，不是某活动的最终授权；尤其旧字段名中含考勤单提交的能力，不能直接当作新版每个考勤动作的授权证明。[B1]

### 8.2 统一动作状态

建议用以下**客户端模型**，不是后端已有字段承诺：

```ts
export type ActionAvailability =
  | { state: 'allowed' }
  | { state: 'denied'; reason: string }
  | { state: 'unknown'; reason?: string }
  | { state: 'unavailable'; reason: string };
```

- `allowed`：展示可操作；未来提交时仍由后端复核。
- `denied`：有确定的不允许原因。
- `unknown`：尚未读取或无法确认，禁止乐观放行。
- `unavailable`：服务未接通或当前功能停用。

不要用 `Boolean(undefined)` 掩盖“未知”，不要使用角色名称直接推导管理权限。

### 8.3 验收场景

普通成员输入负责人 URL、只负责报名的人进入考勤工作台、只负责 A 活动的人访问 B 活动、页面打开后职责被撤销，都要正确拦截或停止动作。

按钮隐藏、路由拦截和本地 mock 拒绝只能证明前端交互边界，不能作为真实服务端防越权证明。

---

### 8.4 后台工具的复用边界

`src/srvf-kit/composables/useActionStates.ts` 返回未知时允许调用者退回原 `hasPerms + 状态` 判断，且 `isBlocked` 只拦明确拒绝。该设计服务于已有管理端增强，不应直接搬进尚无完整授权上下文的移动端。[A5]

移动端保留四态模型；影响报名、代签、撤销等关键动作时，必要的当前资格未知必须先查证，不出现“查不到就是允许”。页面级范围和服务端资源存在性保护不能被 UI 文案破坏；对服务端刻意合并的 404 不擅自解释成“该人员存在但无权”。

动态 tabs 必须显式绑定激活项，权限变化后重新选择第一个可见 tab；测试断言默认内容实际出现，不只断言 tab 标题。这是移动端预防性验收要求，不是本轮断言后台当前仍有该缺陷。

## 9. 数据访问接口与客户端模型

### 9.1 统一访问路径

```text
页面／组件
  → 功能 composable 或少量 store
  → 数据访问 Port
  → mock 适配器 / unconfigured 适配器
  → 现在先写 wire 请求／响应适配并离线测；下一阶段才启用真实 NetworkTransport
```

页面不知道后端 URL、HTTP 包装、数字错误码和 token。未来更换数据源主要在适配器内完成，不保证所有页面完全不改——真实契约缺口可能需要调整展示。

### 9.2 建议的数据访问接口

下表为客户端内部方法语义，不要求后端新增同名 API。

| 接口                | 主要方法                                                                                                           |
| ------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `AuthPort`          | restoreSession、login、refreshSession、logout、getCurrentMember                                                    |
| `ActivitiesPort`    | list、getDetail、getMyParticipationContext                                                                         |
| `RegistrationsPort` | getForm、submit、getResult、cancel、getMyActivities                                                                |
| `InsurancePort`     | getMyOverview、getEligibilityForActivity、createSelf、updateSelf、deleteSelf                                       |
| `AttendancePort`    | getMyState、submitPunch、getMemberCredential                                                                       |
| `ManagedPort`       | listActivities、getScope、listRegistrations、executeAllowedReview、getOnsiteOverview、getQr、staffScan、proxyPunch |
| `ParticipationPort` | getSummary、listRecords、getRecordDetail                                                                           |

不要仅因为某个方法列在表中，就认为真实后端已经存在对应完整读面。所有不足进入接口缺口台账。

### 9.3 页面模型与后端 DTO 分离

应有独立类型表示：

- `CurrentMember`：身份摘要与准入状态。
- `ActivityListItem`、`ActivityDetail`：活动安全展示模型。
- `RegistrationFormDefinition`：题目、约束、版本和显示顺序。
- `RegistrationResult`：报名头与逐场次结果，不能合并成一个状态。
- `InsuranceOverview`、`ActivityInsuranceEligibility`：当前概览与指定活动资格分开。
- `PunchState`、`PunchReceipt`：当前现场状态与某次动作回执分开。
- `ManagedActivityScope`：活动范围与动作状态。
- `ParticipationSummary`、`ParticipationRecord`：正式汇总与记录，不靠页面自行结算。

报名状态、分配结果、考勤状态、审核状态和入账状态分别建类型，禁止共用一个万能 `status` 字段。

### 9.4 本人资格视图示例

下面是客户端契约设计，**不是后端已实现响应**：

```ts
export type ActivityInsuranceEligibility = {
  activityId: string;
  required: boolean;
  status: 'eligible' | 'ineligible' | 'unknown' | 'unavailable';
  explanation: string;
  source?: 'self' | 'team';
  checkedAt?: string;
  action: 'none' | 'manage-insurance' | 'contact-admin' | 'retry';
};
```

`unknown`／`unavailable` 不能转换为“无保险”，`eligible` 只表示系统报名条件结论，不表示已经核实所有保险免责条款或承诺实际理赔。

### 9.5 统一加载与错误模型

```ts
export type LoadState<T> =
  | { state: 'idle' }
  | { state: 'loading' }
  | { state: 'ready'; data: T }
  | { state: 'empty' }
  | { state: 'failed'; error: AppError };

export type AppError = {
  kind:
    | 'not-configured'
    | 'unauthenticated'
    | 'forbidden'
    | 'not-found'
    | 'validation'
    | 'conflict'
    | 'rate-limited'
    | 'network'
    | 'service-unavailable'
    | 'business-rejected'
    | 'result-unknown'
    | 'contract-mismatch'
    | 'cancelled';
  message: string;
  fieldErrors?: Record<string, string>;
  retryAfterSeconds?: number;
  requestId?: string;
};
```

真实数字错误码以后在适配器内映射；本阶段不要发明 BizCode 数字并假装来自后端。

### 9.6 增加“离线契约层”，把接线准备做实

**只做 Port mock 不足以判定接线就绪。** 它能证明页面和模拟业务联动，但绕过了真实字段、信封、媒体类型、错误码与请求白名单。本阶段必须并行完成下面这条无网络测试路径：

```text
页面业务模型 ← mapper ← 已核对的后端 wire 响应
页面提交意图 → serializer → 已核对的后端请求
                               ↓
                     注入 FakeTransport（仅测试）
                     返回合成 JSON / SVG / 错误响应

正式接线时：复用 serializer / mapper / 错误解析
           仅在获准后注入实际 NetworkTransport
```

运行时仍只有 mock/unconfigured；测试层不是第三种可被用户启用的“假线上模式”。不要为此另搭 BFF、独立 mock HTTP 服务或多套请求框架。

#### A. 固定契约快照

在 `contracts/manifest.json` 记录后端 repo、精确 SHA、来源路径、blob／文件 SHA256、选取范围、提取方式／工具版本与核对日期。只纳入本期使用的 Auth/App 端点和其必要依赖类型；不能把包含后台权限的全量 Admin client 导入前端。

- 能取得固定 OpenAPI／生成 App client 时优先取其相关切片，并和 DTO／controller 的实际字段核对。
- 没取得 OpenAPI 文件，就如实记“源码 DTO 切片”，不能编造 OpenAPI hash 或声称已生成客户端。
- 更新契约使用显式本地输入文件或经批准的源码快照；普通 build/CI 不自动拉取远程 main，也不请求 `/api/docs-json`。
- 响应类型来自后端；页面模型属于前端。二者通过 mapper 连接，禁止 `as any`、把页面自造字段塞进后端 DTO。

#### B. 每个 Port 方法必须有能力对照

| 字段               | 要求                                                                        |
| ------------------ | --------------------------------------------------------------------------- |
| 页面／用户任务     | 哪一页、完成什么动作                                                        |
| Port 方法          | 前端内部语义                                                                |
| 实际 endpoint      | 已核实才填写方法和路径；否则 `UNCONFIRMED`                                  |
| sourceRef          | 固定 SHA、文件和行范围                                                      |
| request / response | 精确字段、必填／可空、分页、单位与返回媒体类型                              |
| 权限与状态         | 当前成员、活动职责、业务状态、部署开关分别记录                              |
| retryPolicy        | `safe-read / operation-key / event-key / version-only / none`               |
| resolution         | 原操作可如何查证；没有读取能力就标缺口                                      |
| readiness          | `MOCK_ONLY / CONTRACT_VERIFIED / WIRE_TESTED / LIVE_VERIFIED`，禁止自动升级 |

一个 Port 可以组合多个只读端点，但不能越权读 Admin 接口，也不能偷偷用旧考勤兜底。跨接口缺字段就保持 unknown，不在前端编造“可信”的值。

#### C. 本阶段必须完成的 wire 测试

| 类型           | 检查点                                                                             |
| -------------- | ---------------------------------------------------------------------------------- |
| JSON 信封      | code/message/data、null data、错误信封、204 或无 body 的端点只能按各自契约处理     |
| 参数序列化     | 路径 ID、query、分页、数组、undefined 与 null；禁止将 UI 模型整个展开为请求        |
| 运行时数据边界 | 缺必需字段、类型错、未知状态、无效日期、非有限数字；不把解码失败显示成零数据       |
| 二维码图片     | 成功可能是 SVG 二进制，不套 JSON 信封；失败可能是 JSON，按 Content-Type 与状态分流 |
| 附件           | FormData 字段、大小和类型、一次性上传会话；不能拿本地预览 URL 当附件 ID            |
| 身份生命周期   | login→me→capabilities、refresh 轮换、403／401 区分、退出后的迟到响应               |
| 写入恢复       | 同键同体、同键异体、expectedVersion 冲突、无键 POST 响应丢失                       |
| 精度和时间     | Decimal 字符串、零与 null、秒／小时、北京业务日与 UTC 传输语义                     |

已知认证规则现在就按 [N1] 落入验证；不能继续把所有长度规则写为“以后再说”。未知真实字段则明确留为 gap，不凭设计稿反向要求后端迁就。

请求严格遵守已确认白名单；响应兼容无害新增字段，但关键字段／枚举不认识时要安全降级或停止依赖动作。未知枚举不能被默认为 pass、insured 或 in-service。

#### D. mock 与 wire 不得各讲一套故事

模拟 UI 场景和 wire 契约 fixture 分层维护。已证实端点的成功／失败语义必须一致；拟议读面以 `PROPOSED` 标记，不能冒充真实 HTTP 响应。场景数据是合成数据，不复制真实保单、人员、token 或请求日志。

## 10. 表单、格式与业务前置验证

### 10.1 校验职责表

| 校验                         | 前端现在做                 | 后端接线后必须做         |
| ---------------------------- | -------------------------- | ------------------------ |
| 必填、格式、字符串长度       | 做并测试                   | 再校验                   |
| 起保日不晚于到期日           | 做并测试                   | 再校验                   |
| 题目数量、选择数量、字段版本 | 根据数据定义验证           | 核对当前权威版本         |
| 文件格式／大小提示           | 本地初筛                   | 内容校验、存储、安全检查 |
| 是否符合保险要求             | 读取 mock 结论，不自行认定 | 唯一权威判断             |
| 报名资格、名额、候补、分配   | 展示 mock 结果             | 唯一权威判断             |
| 二维码真实性、签名、有效期   | 只做格式与场景提示         | 必须服务端验证           |
| 位置与签到时间窗             | 采集或模拟，不自行放行     | 必须服务端验证           |
| 时长、贡献与最终认定         | 只展示                     | 必须服务端认定           |

### 10.2 通用规则

- 文本去空白策略按字段定义，密码不去空白。
- 必填检查不能把数字 `0` 和合法布尔 `false` 当作空值。
- 首次打开表单不满屏报错；字段失焦及提交时显示合理反馈。
- 提交失败后保留可安全保留的输入，滚动并聚焦第一个错误字段。
- 前后端错误能定位到字段时内联展示，无法定位的在表单顶部展示。
- 校验函数独立于 Vue 组件，测试边界值和不合法输入。
- 兼容未知状态、未知题型和不完整数据，禁止默默丢弃必答项后继续提交。

### 10.3 动态报名八类题型

参考版本已有八类题型；本阶段按此渲染，不硬编码某一次活动的问题。[B3F]

| 题型            | 必须实现的输入及验证                                         |
| --------------- | ------------------------------------------------------------ |
| `short_text`    | 单行、必填、最小／最大长度                                   |
| `long_text`     | 多行、字数提示、长度约束                                     |
| `number`        | 合法有限数字，支持 0，按配置判断上下界；不接受 NaN／Infinity |
| `date`          | 合法日期字符串、闰年、月份天数；不擅自按设备时区改一天       |
| `single_choice` | 只能选择给定选项，必填时不能为空                             |
| `multi_choice`  | 数组去重、选项白名单、选择数量上限                           |
| `file`          | 本地选择、大小／格式提示、删除／重选；状态是未上传           |
| `confirmation`  | 要求确认时必须明确勾选，不默认勾选                           |

题目 `fieldCode`、类型、约束和选项都来自可信的模拟定义。动态键处理避免 `__proto__` 等特殊属性污染；不使用 `eval` 或动态执行模板。

### 10.4 场次与岗位

- 同一场次不能重复选择，同一岗位不能重复出现在志愿序列。
- 岗位必须属于对应场次；不能把岗位 ID 当作全局职务 ID。
- 有岗位的场次按配置要求选择；无岗位场次不强迫填一个虚拟岗位。
- 支持多个场次和有序岗位志愿；排序明确，不根据 DOM 顺序猜测。
- 可用性／容量发生变化，返回冲突说明并重新获取模拟最新定义，不覆盖用户全部输入。
- 表单版本变化时提示重新核对；不能把旧版本答案静默绑定到新题目。

### 10.5 自购保险表单

| 字段     | 本阶段验证                                              |
| -------- | ------------------------------------------------------- |
| 保险公司 | 非空；参考当前字段上限 128 字符                         |
| 保单号   | 非空；参考当前字段上限 128 字符；不擅自限定纯数字       |
| 起保日期 | 支持既有可空值；鼓励填写，填写后必须是合法日期          |
| 到期日期 | 必填、合法日期                                          |
| 日期组合 | 起保日存在时不得晚于到期日                              |
| 修改版本 | 保留 `expectedVersion` 语义，模拟冲突后刷新，不强制覆盖 |

不能因为填了保单号、日期有效，就在前端写入“审核通过”。登记仅表示提交资料；自购审核由授权管理流程完成。团队统保为本人只读，不让队员自行把自己加入覆盖名单。[B7]

当前有效与本次活动可用不同：例如今天有效但活动前到期、活动当天尚未起保、只覆盖多日活动的一部分，均应有独立模拟场景。具体资格结论由模拟接口返回，不在正式页面重写保险算法。

### 10.6 文件本地选择

- 报名附件参考当前约束：JPEG、PNG、WebP、PDF，单文件不超过 10 MiB；作为集中配置，不分散硬编码。[B3U]
- 文件名、后缀、MIME 与大小只用于前端初筛，不宣称已完成安全检测。
- 图片可本地预览；PDF 至少展示文件名与大小，不依赖外部在线预览服务。
- 选择后显示“已选择，尚未上传”；模拟提交需要演示附件已接收时，也明确是模拟。
- 释放不再使用的对象 URL，不把文件转为 Base64 长期存入浏览器存储。
- 文件重选、删除、大小超限、类型不支持、空文件、模拟上传失败都要可演练。
- 文件信息不进入 URL、日志和错误截图；页面刷新后需要重新选择时明确提示。

## 11. 报名与保险之间的返回流程

```text
活动详情／报名表
  → 模拟保险资格不满足
  → 去“我的保险”
  → 新增或修改自购保险
  → 提交资料（模拟）
  → 显示待审核，不自动通过
  → 返回原报名页面
  → 重新获取模拟资格
  → 若已由模拟管理场景确认，才恢复提交入口
```

实施要求：

- 保留原活动、选中的场次岗位和安全的草稿内容。
- “返回报名”是返回原业务，不是简单跳活动首页。
- 不因用户访问过保险页面或点击“我已购买”就放行报名。
- 待审核、审核未通过、已过期、未生效、统保存在、资格读取失败有不同提示。
- 统保接口缺失时显示“暂无法确认”，不能反向要求所有人重复买保险。
- 首发正常演示活动均设置保险要求。后端是否强制所有实际活动、是否采用严格审核，留在接线检查；前端不擅自提供关闭保险要求的开关。
- 不创建保险审核移动后台；审核结果变化通过场景面板模拟，不嵌入普通队员页面。

## 12. 提交、防重复、冲突与未知结果

### 12.1 每个写操作采用明确状态

```text
idle → validating → confirming（需要时）→ submitting
                                           ├─ success
                                           ├─ rejected
                                           └─ result-unknown
```

- 按钮 loading 与禁用只是交互防抖，不等于业务幂等。
- 报名提交、扫码、代签、取消和保险更新都用统一的提交状态辅助函数。
- 重复点击、回车、快速返回再进入，不应产生两次相同模拟业务事件。
- 对真实契约有操作键的命令，同一意图保留同键同体；不支持幂等键的端点只做本地防连点，不能自行添加一个 key 冒充服务端已支持。具体见 §12.4。
- mock 层与离线 wire 测试只对支持的命令模拟同键同载荷重放／异体冲突；无键写入必须演练响应未知后的查证，不复制后端事务实现。

### 12.2 超时不等于失败

模拟“动作已被接收，但回执丢失”：页面显示“结果暂未确认，请查询”，而不是立即显示失败或自动重发。

提供查询原结果的行为；有后端契约支持时才允许用户显式重试原意图。复杂写操作禁止通用自动重试，更不能换键重试造成重复报名或打卡。

### 12.3 并发与版本冲突

保险编辑冲突、二维码版本更新、表单版本变化、人员职责撤销都要有模拟测试。

发生冲突时显示“资料已发生变化，请刷新后核对”，保留可安全保留的编辑内容，不使用强制覆盖作为默认解决方式。

---

### 12.4 写操作按真实能力分类，禁止“万能重试”

| 操作                             | 参考契约能力                      | 前端策略                                                               |
| -------------------------------- | --------------------------------- | ---------------------------------------------------------------------- |
| 新版报名命令                     | `operationKey`                    | 保持原键、原表单版本与原载荷；是否允许精确重放仍按端点和当前资格       |
| 场次打卡／受控代签               | `eventKey`                        | 保持原意图、原凭证及原位置快照；**不能用同键重新采一组坐标**           |
| 二维码签发／撤销                 | `operationKey`                    | 保留原意图，响应丢失先核对版本／状态；不能自动重签另一张码             |
| 自购保险更新／删除               | `expectedVersion`，不是通用重放键 | 先重新读当前记录并比对；版本号不能当成“这个请求一定没执行”的证明。[N2] |
| 自购保险新增、部分取消／审核入口 | 未核实有幂等键                    | 禁用通用自动重试；不能擅自加 operationKey；查证或人工处理              |
| 认证 refresh                     | 凭证轮换                          | 遵循 §7.8，不因超时自动重复使用旧 refresh                              |

上表是固定版本的对接边界，实施时每个实际调用仍须绑定 sourceRef。没有确认原操作查询端点时，不能凭空实现“查原操作结果”HTTP 路由。

### 12.5 未知结果、刷新页面与隐私不能互相矛盾

旧稿“退出清理一切”与“始终可原键原体恢复”需要拆开：浏览器丢失原始载荷后，不能承诺还能够安全重放。

- 写入前建立本地意图记录：actor/session epoch、operation 类型、资源、键（存在时）、载荷摘要、阶段。摘要仅作一致性保护，不是授权或后端事实。
- 密码、refresh token、完整保单、二维码凭证、精确坐标和文件正文默认只在内存；不为重试方便整包落 localStorage。
- mock 使用纯合成数据，可以持久化演示意图以测试刷新；真实接线不能直接沿用该存储方案。
- 已发送且响应未知时，禁止对同一对象新建替代意图。页面刷新后若只剩安全的查证标记，先查询已有权威读面；不存在读面时显示“结果待核实，请联系负责人”，不自动重新提交。
- 丢失原 qrToken／坐标／文件会话后，不可用同 eventKey 重新采样重放；缺少精确载荷要走查证或重新确认的业务流程。
- 退出必须清除当前账号内容并终止后台任务；如保留不含敏感数据的未决提示标记，须按原 actor 隔离、设期限，不能展示给新账号或自动恢复执行。隐私策略不允许保留时清除，并明确再次登录需从权威记录核对。
- `AbortController.abort()`、关页、前端取消等待都不代表服务器取消了写操作。原操作是否生效只有后端可确认。

这部分现在用模拟／离线契约测试完成；真实未知结果恢复方案未获得契约支持的操作，不能标为 CONTRACT_READY。

## 13. 草稿、缓存与离开提醒

| 数据                             | 默认策略                                     |
| -------------------------------- | -------------------------------------------- |
| 列表筛选、滚动位置               | 会话内保存；可存非敏感 UI 偏好               |
| 报名场次／岗位选择               | 按账号、活动和表单版本隔离的会话草稿         |
| 动态答案                         | 默认内存；字段敏感性不明时不落浏览器持久存储 |
| 保单号、密码、扫码凭证、精确位置 | 不持久化到浏览器存储                         |
| 本地选择文件                     | 仅内存；刷新或退出后提示重新选择             |
| 模拟会话及固定合成场景           | 可以存入专属 mock 命名空间，用于刷新演示     |
| 真实业务数据                     | 本阶段不加载、不保存                         |

规则：

- 用 `dirty` 判断确有未保存修改；原值未变不弹提醒。
- 提交成功、主动丢弃、退出账号后清理对应草稿。
- 返回保险页面后可以恢复当前会话内的报名草稿；刷新后敏感字段和文件不保证恢复，需提前提示。
- 不把“浏览器离开提醒”当作永不丢失保证。
- 没网时不把打卡命令放入后台队列自动补交。本阶段没有离线考勤，避免补交时间与现场事实不一致。
- 场景数据库允许在切换模拟队员和模拟负责人后继续演练，但页面缓存和身份权限必须重置；不能把跨角色共享场景误写成共享用户数据。

## 14. 扫码、相机、定位与本地设备能力

### 14.1 设备能力与业务 API 分离

浏览器相机和定位不是业务服务器接口，可以先实现能力检测、授权提示、资源释放及本地演练。但默认模拟场景不索取设备权限，只有用户点击“测试相机／定位”后才请求。

相机和定位需要相应安全上下文与用户许可；因此桌面模拟成功不能视为手机微信环境已经兼容。[T6][T7]

### 14.2 适配器边界

| 适配器               | 本阶段必须具备                                                       |
| -------------------- | -------------------------------------------------------------------- |
| `ScannerAdapter`     | 启动、停止、识别结果、无效码、重复识别控制、错误反馈；可替换解码实现 |
| `CameraAdapter`      | 支持性检测、用户触发申请、拒绝／不可用、切后台和离页释放             |
| `LocationAdapter`    | 不要求／需要授权／获取中／成功／拒绝／超时／不可用状态               |
| `CredentialRenderer` | 显示本地合成二维码或静态演示图，释放 Blob URL                        |

扫码解码只选一种轻量实现，依赖和版本由执行时核对并记录。不得同时引入多套扫码库，不把微信 JS-SDK 和普通浏览器能力混成一个无条件调用。

### 14.3 二维码演示格式

- 演示码采用明显的专属前缀，例如 `SRVF-DEMO:`，只能在 mock 场景识别。
- 区分 `session-check-in`、`session-check-out`、`member` 三类，不可相互替代。
- 不制作或伪造真实后端签名；正式 token 的解码、认证仍是后端职责。
- 能生成本地合成二维码并以本地图片完成识别测试；真实相机未测试时明确记为 NOT_RUN。
- mock 模式拒绝将任意真实二维码当演示凭证，不自动访问扫码得到的 URL。
- 不将二维码内容写到地址栏、持久存储、埋点、控制台或错误报告。

### 14.4 扫码状态与生命周期

```text
idle → requesting-permission → scanning → recognized
                                      → confirming → submitting → result
        └─ denied / unavailable / cancelled
```

识别到一个码后先暂停识别，避免摄像头连续帧重复提交。当前动作未结束时不得自动扫描并发起第二次写操作。

关闭弹层、切换路由、退出账号和组件卸载时都要停止相机轨道、清理监听器及定时器。应用回前台后重新读取状态，不沿用旧许可或旧二维码有效性假设。

### 14.5 定位与时间窗

- 活动不需要定位时不申请定位；需要定位但策略未知时不擅自默认“不需要”。
- 位置信息只用于当前动作，默认不保存精确坐标。
- 经纬度、精度格式可以前端验证，但不由前端断言在签到范围内。
- 坐标系在真实接线时核对；不得将不同来源坐标直接混用。
- 倒计时使用数据源提供的 `serverTime` 与 `checkOutAllowedAt` 语义；倒计时到零后重新确认状态，不自动签退。
- 参考版本存在普通签退最短时段校验，前端不要另写一份可绕过的业务规则。[B4]

### 14.6 无设备权限时的兜底

明确提示如何开启权限或联系现场考勤负责人。模拟版可切换到预置演示码继续验收，但该调试入口不得出现在普通构建中。

“由负责人核验”是一条受控业务流程，不是一个普通队员自己点选的权限绕过按钮。

---

### 14.7 首发扫码入口与真机边界

**首发默认“先进入 H5 的场次考勤页，再点扫一扫”。** 不默认承诺微信首页扫一扫会自动打开 H5 并完成签到：后端二维码可能承载签名凭证而不是可跳转网页地址，必须另核实载荷与入口契约。不得为了做跳转把原始凭证放进 URL、埋点或浏览器历史。

相机、解码器、凭证校验是三件事。前端解出文字不等于真实凭证有效；场次与动作不符必须提示重新扫描，不能自行切换到另一个写操作。

设备生命周期还须覆盖：应用切后台、锁屏、来电／相机占用、返回前台、浏览器 BFCache 恢复、用户一直不处理授权提示。晚到的 MediaStream 若已离页，立刻停止全部轨道。定位超时和弱精度不是“坐标为 0”；不得伪造位置信息。[T6]

真机验收记录设备型号、系统、浏览器／微信版本、HTTPS 方式、授权结果和实际扫码结果。电脑 WebKit、UA 修改和图片解码都不能替代 iPhone／微信真机证据。没有设备时，前端可继续交付，但设备相关 RELEASE_READY 保持阻塞。

## 15. 时间、数字、文案与展示规范

### 15.1 时间口径

- 面向救援队的业务时间按 `Asia/Shanghai` 展示，不随浏览者电脑时区改变活动日期。
- 明确区分时间戳与 `YYYY-MM-DD` 日期。保险保障日期按日期语义处理，不擅自把日期转为本地午夜再跨时区偏移。
- 跨日、多日活动明确写日期，不只显示“08:00—17:00”。
- 模拟业务使用注入时钟；普通展示可获取真实当前时间，但不能用它决定正式资格。
- 所有倒计时和轮询在离页后停止，切后台后不无上限积累请求。
- 真实接口若以 UTC 自然日过滤活动，接线时必须单独对齐，不把北京时间日期原样发送后假装语义相同。

### 15.2 数字与空值

- `null`／未提供显示为“暂无／待确认”，不能显示成 `0`。
- 正式服务时长与贡献值保留数据源精度，页面只做展示格式化。
- 区分秒、小时、积分、人次；不要把字段重命名后混算。
- 分页记录不能当完整统计分母。
- 认定中、未认定、认定为零分别显示。

### 15.3 文案规则

使用队员能理解的词：报名已提交、候补中、保险待审核、签到已记录、考勤待确认、正式时长。

不把技术词 `committed`、`revision`、`cutover`、`PunchEvent` 直接展示给普通队员。技术状态可以在开发场景面板查看。

重要区分：

| 不应出现的误导                     | 正确表达                         |
| ---------------------------------- | -------------------------------- |
| 提交报名后直接显示“报名通过”       | 已提交；具体场次结果见下方       |
| 新增保单后显示“保险验证成功”       | 保险资料已登记，等待审核         |
| 扫码成功后显示“服务 8 小时已到账”  | 签到／签退已记录，正式结果待认定 |
| 请求超时显示“操作失败，请重新提交” | 暂未确认结果，先查询原操作       |
| 没查到统保就显示“你没有保险”       | 当前无法完整确认保障情况         |
| 页面隐藏按钮即显示“已防越权”       | 前端展示已限制，服务端授权待联调 |

#### 15.4.2 三层样式，不把后台工程搬过来

```text
固定来源品牌值 tokens.brand.css
        ↓
移动端语义与尺寸 tokens.mobile.css
        ↓
Vant 映射 vant-theme.css + 少量业务组件样式
```

- 初期复制所需 token 及出处、blob／hash 记录即可，不新建 npm 共享包或跨仓实时依赖。
- 不导入后台 `index.scss`、sidebar、Element Plus、PureAdmin table 或桌面布局。
- 使用本地 SVG／Vant 图标，禁止复制在线 Iconify 请求链或外链字体。
- 队徽需核对真实 SRVF 资产路径和可用文件；尚未确认时用清楚的文字标识，不能把模板 logo 当队徽，也不擅自绘制替代队徽。
- 中文字体走系统回退。保留原字体族名不会自动下载字体；不加入 Google Fonts 外链。
- 首版只交付浅色主题；不因后台有 dark 模式就扩范围。

映射示例，具体覆盖项随所锁定 Vant 4 版本做计算样式测试：[T11]

```css
/* 在 Vant 样式之后载入。品牌基础变量来自固定的 SRVF token 文件。 */

  --van-primary-color: var(--srvf-accent-primary);
  --van-danger-color: var(--srvf-red);
  --van-text-color: var(--srvf-fg-default);

  --van-background-2: var(--srvf-bg-surface);
  --van-border-color: var(--srvf-border-default);
  --van-base-font: var(--srvf-font-sans);
  --van-radius-sm: var(--srvf-radius-sm);
  --van-radius-md: var(--srvf-radius-md);
  --van-radius-lg: var(--srvf-radius-md);
  --van-font-size-xs: var(--srvf-text-xs);
  --van-font-size-sm: var(--srvf-text-sm);
```

#### 15.4.3 品牌值不等于所有组合都可读

本轮用 sRGB 相对亮度公式计算以下色对白底、不透明条件下的对比度（展示两位小数，验收比较未舍入值）：

| 前景／底色              | 对比度约值 | 使用结论                               |
| ----------------------- | ---------- | -------------------------------------- |
| 救援红 `#C4001B` / 白   | 6.24:1     | 正常正文色对达到 4.5:1 门槛            |
| 盾蓝 `#19478A` / 白     | 9.09:1     | 正常正文可用                           |
| 次要文字 `#5E6A80` / 白 | 5.46:1     | 正常次要正文可用                       |
| 在岗绿 `#2E8B57` / 白   | 4.24:1     | 不直接用于普通小字号绿色文字或白字绿底 |
| 待命琥珀 `#B26A00` / 白 | 4.24:1     | 同上，应使用深色正文配状态标记         |
| 荣誉金 `#C9A24A` / 白   | 2.40:1     | 装饰，不承担必要文字                   |
| 灰 `#9AA4B6` / 白       | 2.51:1     | 不能承载“无法确认”等关键说明           |

一般正文采用至少 4.5:1，较大文字适用 3:1；真正不可操作控件等有特定例外，但不能把重要提示归为“禁用”逃避可读性。[T12]

保留品牌原色，第一版优先用“深色文字 + 彩色点／图标／浅底 + 明确文案”表达状态。确需状态专用文字色时，在 `tokens.mobile.css` 新增可访问的语义变量并附对比度测试，不篡改基础色或宣称整套 UI 已通过 WCAG。

品牌红表示主要操作，红色告警需同时有错误图标和明确文案；不能靠“按钮是红色”区分普通报名与危险撤销。当前导航也需图标／文字／选中形态，不只改变颜色。

#### 15.4.4 设计系统必须有可验收页面

在仅 mock 可见的本地组件预览中集中展示：按钮各态、输入错误、状态标签、保险资格卡、活动卡、长表单、全屏码、空／错／未知状态、模态确认和底部操作栏。无需新建 Storybook 平台。

`pnpm check:tokens` 至少验证：关键品牌值匹配；不存在无定义变量；主按钮／Tab／表单 focus／弹层实际计算样式与映射一致；重要文本色对达到项目要求；未意外加载 Vant 默认蓝色或后台 `--el-*`；页面没有分散写死品牌十六进制值。

Vant 原生状态类型也要经过本项目状态组件包装；不能未经色对检查直接用白字绿底／琥珀底的小标签。首版优先深色标签文字配彩色图标，不改变品牌基础色。

### 15.5 移动端可用性

- 延续 SRVF 品牌，但为单手操作、现场强光和手机屏幕重新组织布局，不压缩桌面表格。
- 标题、状态、主按钮层次清楚；一个区域尽量只有一个最重要动作。
- 主要触控目标建议不小于 44×44 CSS 像素；这是项目验收要求。
- 320、375、390、430 像素宽度下不出现整页横向滚动。
- 适配底部安全区、软键盘、长姓名／外号、长活动名、长保单号与文件名。
- 底部固定操作栏不能遮挡最后一个字段、错误提示和浏览器按钮。
- 不能只靠红绿颜色传递状态；文字和图标同时提供含义。
- 对话框具备标题、焦点与键盘操作；错误可被辅助技术识别。
- 保留浏览器缩放能力；不用动画掩盖慢请求，也不用复杂转场拖慢操作。

### 15.6 性能、页面恢复与故障提示

- 账户、权限、保险、报名等状态由统一页面模型提供，不在组件里建立第二份事实。
- 扫码解码器、PDF 预览等较重依赖延迟到使用时加载；本期不接在线地图、全量图表库与远程字体。
- 建议首屏必要 JS+CSS gzip 总量目标不超过 350 KiB（不含后续扫码独立 chunk）。这是项目预算，不是已测结果；实际超出需给明细和合理解释，不能通过删错误处理或测试规避。
- 浏览器返回缓存／长时间后台恢复时重新检查身份与必要数据，恢复前不闪现旧账号内容。请求 key 至少包含 actor、活动、场次、筛选和数据模式。
- 动态 import／资源版本失效应提示刷新；有未保存或结果未知的写操作先处理上下文，不无限自动 reload。
- 正式结果为空、读取失败、尚未认定要分别显示；后端服务未就绪不是“你没有参与记录”。

## 16. 模拟数据与场景体系

### 16.1 模拟数据必须可复现

采用固定 seed 和可控制时钟，例如将默认演示时钟固定为 `2026-11-15 08:00:00 Asia/Shanghai`。活动相对该时钟生成，测试不依赖真实当天。

模拟延迟、失败与状态变化由场景参数控制，不使用随机数决定成功率。刷新、重置和自动化重跑应能得到相同结果。

### 16.2 最少准备的身份

| 场景身份       | 用途                                 |
| -------------- | ------------------------------------ |
| 演示队员 A     | 正式成员，有自购保险，普通报名和考勤 |
| 演示队员 B     | 正式成员，只有团队统保               |
| 演示志愿者     | 受邀可见与非正式成员可见性           |
| 演示报名协办   | 只能管理活动 A 的报名                |
| 演示考勤协办   | 只能管理活动 A 的现场考勤            |
| 演示双职责成员 | 报名和考勤职责均有                   |
| 演示未绑定账号 | 登录后不能进入成员功能               |
| 演示停用成员   | 准入被拒、会话清理                   |

名称、编号、保单、头像、资料全部使用合成数据；不复制队伍真实名单或本会话中出现过的测试凭证。

### 16.3 最少准备的活动

至少 6 个：单场次正常活动、多日多场次活动、有岗位志愿活动、受邀活动、已截止／已满活动、已结束的历史活动。

其中至少一个活动有自定义表单和附件题，至少一个有“上午通过、下午候补”的混合结果，至少一个用于权限跨活动拒绝测试。

## 17. 安全、隐私与日志底线

### 17.1 不收集真实数据

- 登录、保险和附件页均提示为模拟演示，勿输入真实账号密码或保单。
- 不接第三方统计、错误上报、客服 SDK、在线字体与远程图片。
- 控制台和执行报告不包含密码、二维码凭证、保单号、精确定位及文件正文。
- 演示截图只使用固定合成数据。

### 17.2 内容安全

- 活动说明与题目文案先按纯文本或受控结构渲染。
- 不将未知内容作为 Vue 模板，不无条件使用 `v-html`；如未来确需富文本，另定清洗与链接策略。[T8]
- 二维码图片通过受控图像展示，不把任意返回字符串直接当可执行 SVG 内联进 DOM。
- 对文件 URL、外部链接、跳转目标和动态字段键做必要校验。

### 17.3 本地存储不是权限来源

真实接线后必须重新验证身份和活动职责。浏览器缓存的能力、曾经访问成功的页面、按钮是否存在，都不能证明现在仍然有权。

本阶段关于登录态和权限的 PASS，只指前端与 mock 演练；真实认证、防越权、撤权即时性、安全存储和并发约束均需后续真实联调。

### 17.4 日志要求

调试日志仅记录合成场景 ID、动作类型、耗时、非敏感错误类别；默认关闭详细 payload 打印。

操作回执可以显示模拟请求编号方便追踪。出现错误时不得把整个请求体或整个 store 自动输出。

| 新版报名               | `POST /api/app/v1/activities/:activityId/registrations`                                    |
| 自购保险               | `/api/app/v1/me/insurances` 及单条修改／删除                                               |
| 新版场次打卡           | `/api/app/v1/activities/:activityId/sessions/:sessionId/punches/*`                         |
| 本人打卡状态           | `/api/app/v1/activities/:activityId/sessions/:sessionId/my-punch-state`                    |
| 场次码与负责人现场操作 | `my/managed-activities` 下对应 QR 与 onsite 控制器                                         |
| 本人参与               | `/api/app/v1/my/participation-ledger`、`participation-summary`、`participation-time-proof` |

后续接线开始时，以当时部署的精确契约重新核对；不批量照搬旧 SDK，不调用旧 `my/activities/:id/check-in` 或旧考勤单写链。

### 18.3 不得被延后的判断边界

即使尚未接 API，现在也必须确定：未知结果怎么显示、无权限如何退出、保险不符合怎么返回、扫码失败如何恢复、历史活动不可读怎么兜底。

这些属于前端设计工作，不应全部写成 TODO 留给联调时临时处理。

### 18.4 现在交接给后端的五类核心读取缺口

“页面先做”不等于把缺口拖到正式上线。以下应在开发早期整理为一张可交付表，复用已有服务和安全投影，不预设新增路径、不要求为 UI 重写领域逻辑：

| 交接项                       | 页面最低需要                                                                 | 判定阻塞的范围                                 |
| ---------------------------- | ---------------------------------------------------------------------------- | ---------------------------------------------- |
| 本人保险概览与本活动保险资格 | 自购／统保安全摘要、本次活动是否要求、满足／不满足／未知、原因与检查时间     | 完整保险引导与预检；最终报名仍必须后端复核     |
| 本人新版报名与场次结果       | 当前答案和表单版本、场次岗位志愿、逐场分配／候补结果、可修改／取消的准确边界 | 本人知道去哪场、哪个岗位；不能只看报名头       |
| 新版现场名单与代签目标       | 安全成员标签、场次、参与身份 ID、当前在场及异常摘要、分页和真正总数          | 负责人按人核验／代签及工作台统计               |
| 本人历史参与上下文           | 已完成／取消／终止活动的最小安全摘要、相关场次、结果来源                     | 历史详情不白屏、不借公开活动详情越权           |
| 新版正式结果与处理进度       | 正式净额、分类／单位、适用版本、未认定与零的区分                             | 可用的考勤记录和时长展示，不只是一张原始账本表 |

每项记录：已有服务／端点证据、缺的字段、前端消费方法、谁负责确认、最小验收例、当前状态。未发现不等于一定不存在，应让后端先复核，再判是否最小补充。

**能力冻结而不是接口名称冻结：**页面设计先冻结用户任务和数据语义；后端已满足的路径不另造一套；未满足的 Port 标为 MOCK_ONLY。读面未解决不阻止组件开发，但阻止相关功能标 WIRE_TESTED／可上线。

本轮只生成交接文档，不擅自创建后端 PR、不修改数据库或开关。

### 18.5 四级就绪门槛

| 级别              | 达标要求                                                                                                         | 仍不能声称                     |
| ----------------- | ---------------------------------------------------------------------------------------------------------------- | ------------------------------ |
| UI_READY          | 13 主页面、原 43 场景及新增前端场景、品牌与设备生命周期、零真实请求检查通过                                      | 真实 API 已接通                |
| CONTRACT_READY    | 本期所有拟首发操作都有来源／能力映射，已存在端点离线 wire 测试通过；核心缺口有已确认解决方案，不能仍靠假响应冒充 | 服务部署、真实权限和真机已验收 |
| INTEGRATION_READY | 后端候选 SHA／契约、测试部署、测试身份／活动／保险数据、HTTPS 和跨域方案明确，获得真实联调授权                   | 全链已通过或可直接给队员用     |
| RELEASE_READY     | 真实账号从保险→报名→扫码→负责人处理→管理端认定结算→本人查结果通过；权限负例、真机和发布检查完成                  | 未实际执行的项目可省略         |

允许单个功能标注其就绪级别；不把一部分 mapper 通过写成整个系统 CONTRACT_READY。准备阶段真实 API 和生产部署始终 NOT_RUN。

### 18.6 部署与接线包现在就备好，但不开通

交付一份 `docs/integration-readiness.md`，包括：

- 前端 base／Hash 路由、静态资源根、正式 origin／API origin 占位及同源反代或跨域的备选说明；未批准的不预填真实线上地址。
- HTTPS、相机／定位权限、跨域允许源、Authorization 和请求媒体类型、必要响应头、附件限制、SVG 缓存策略的核对表。
- 拟选凭证存储 ADR、跨标签刷新策略、失效／撤权、退出与日志脱敏方案。
- 前端版本、后端 SHA、契约摘要和 generator 版本的兼容记录；不以 latest 或“已经合并”替代部署证据。
- 本地静态预览配置、未来部署配置模板、环境解析、源映射不公开、静态资源缓存／index 更新策略和出错恢复办法。
- 演示构建与真实构建使用不同产物和存储前缀；未来 API 包不能在服务失败时切 mock；模拟资料绝不迁入真实数据库。
- 发布回退只针对已验证兼容的前端产物，不关后端 v1.1 Gate、不重新启用旧考勤，不擅自回滚迁移。
- 最小真实冒烟顺序与结果表，真实测试账号由获准环境另行准备，不在文档放凭证。

原顺序可以压缩为：**确认后端候选契约 → 对比离线快照 → 接真实传输 → 真实读写与手机验收 → 发布**。不需要等后端对公众开放才安排授权的测试环境联调，但本阶段仍不执行。

## 19. 自动化测试与人工验收

### 19.1 测试层次

| 层次           | 最少覆盖                                                                        |
| -------------- | ------------------------------------------------------------------------------- |
| 单元测试       | 字段校验、日期处理、安全返回目标、状态映射、草稿隔离、提交防重、会话续期协调    |
| 离线契约测试   | 固定 DTO 的请求白名单、响应解析／mapper、媒体类型、错误、按操作分类的重试与查证 |
| 主题与产物检查 | 品牌值、Vant 计算样式、指定色对、字体和图标本地化、普通构建无 mock 数据         |
| 组件测试       | 八类动态题、保险资格卡、状态页、按钮禁用、表单错误、全屏二维码、离开提醒        |
| 浏览器 E2E     | 完整登录／报名／保险／考勤／负责人链、账号切换、网络边界                        |
| 人工检查       | 实际排版、返回、键盘遮挡、长文本、扫码／相机权限、真机环境（能做则做）          |

可以用 Vitest 假时钟验证过期和倒计时，不用让测试真的等待十几分钟。[T9]

### 19.2 必须通过的 E2E 主流程

1. 未登录进入活动深链接 → 演示登录 → 返回原页 → 模拟报名 → 查逐场次结果。
2. 缺少符合条件保险 → 去保险页登记 → 待审核 → 仍不可提交 → 场景面板改变审核状态 → 返回并重新核对 → 报名。
3. 仅有团队统保 → 正常显示满足条件 → 不要求重复登记。
4. 会话临时续期 → 并发请求合并 → 过期处理 → 退出后迟到响应不能恢复旧会话。
5. 队员签到 → 重复扫码 → 未达签退条件 → 推进模拟时间 → 签退 → 仅显示现场回执，不生成正式时长。
6. 报名协办只操作报名；考勤协办只操作考勤；A 活动职责不能操作 B 活动。
7. 负责人代签缺少原因被拦截 → 填写原因 → 模拟回执 → 列表状态一致。
8. 表单版本或保险版本冲突 → 显示原因 → 重新获取并核对，不强制覆盖。
9. 提交已处理但回执丢失 → 结果未知 → 查询原结果 → 不重复执行。
10. 退出／换账号／浏览器后退 → 旧保险、名单、草稿和二维码不再出现。
11. 普通 `build` 产物 → 未接线提示 → 无演示账号与场景面板，配置不能静默回退 mock。
12. 全流程抓取浏览器网络 → 真实业务请求为 0。

### 19.3 适配验收矩阵

- 自动化至少跑 Chromium 和 WebKit；记录实际版本。
- 页面截图覆盖 320、375、390、430 像素宽度，至少覆盖登录、活动详情、长报名表、保险页、现场工作台。
- Playwright 的设备模拟覆盖屏幕、触控、时区等配置，但不是 iPhone 实机或微信内置浏览器认证。[T10]
- 有设备条件时补 Android 浏览器、iPhone Safari、手机微信实测；没有设备就写 NOT_RUN，不把 UA 模拟当真机通过。
- 相机成功、用户拒绝、权限请求被忽略、无摄像头、定位超时分别检查。

### 19.4 不以覆盖率数字代替业务验收

无需追求全项目 100% 覆盖率，但上述关键行为不得缺失。测试必须断言结果，而不是只访问页面、截图就通过。

不允许为了让检查变绿而跳过失败测试、删除关键断言、全局屏蔽类型错误或把关键模块排除覆盖。
